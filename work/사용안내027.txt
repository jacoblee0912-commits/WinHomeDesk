WinHomeDesk 0.2.7 — RDCMan 3.22 기본 엔진의 초기 연결 대기 수정

원인과 수정
- 0.2.6에서는 NLA 암호 인증 후에도 새 엔진이 연결 준비 단계에서 멈출 수 있었습니다.
- RDCMan 3.22는 UDP Shortpath 옵션을 켭니다. 서버가 구현되지 않은 UDP multitransport 지원을
  광고하면서 응답을 기다리는 상태(MULTITRANSPORT_BOOTSTRAPPING_RESPONSE)에 머물렀습니다.
- 서버의 해당 지원 광고를 끄고 구현된 TCP 경로로 연결합니다. 새 엔진 자체를 끄는 방식이 아닙니다.
- 이전 테스트에서 실제 앱의 이 옵션을 빠뜨렸습니다. 이번에는 같은 옵션으로 실패를 재현한 뒤 수정했습니다.
- CS_UNUSED1의 Offset 2/4 경고는 이번 중단의 직접 원인이 아닙니다. 암호를 바꿀 필요는 없습니다.

적용 방법
1. 접속받는 서피스에서 기존 WinHomeDesk를 트레이 메뉴의 '종료 (서버도 종료)'로 완전히 종료합니다.
2. 새 ZIP 전체를 새 폴더에 압축 해제합니다. EXE만 교체하면 안 됩니다.
3. WinHomeDesk.exe를 실행하고 제목의 0.2.7을 확인한 뒤 서버를 시작합니다.
4. 시작 로그의 'TRANSPORT tcp=1 udp_multitransport=0'을 확인하세요.
5. RDCMan 3.22는 기존 CMD 없이 평소처럼 실행하고 기존 RDG로 다시 연결하세요.
6. 접속 계정 surface / 현재 WinHomeDesk 앱 전용 암호를 사용합니다. Windows PIN이 아닙니다.
7. 자동 시작을 사용한다면 새 폴더의 프로그램에서 환경 설정을 저장해 실행 경로를 갱신하세요.

유지되는 기능
- 새 RDCore 엔진 및 기존 MSTSC 엔진용 NLA/TLS 인증, 기존 RDP/RDG 그룹 파일.
- 화면 전송·GPU 인코딩·오디오·한영키·트레이·자동 시작 설정.
- 0.2.6의 오디오 종료 후 재접속 오류 수정과 연결별 인증 처리.
- 인증서, 암호 설정 저장 위치는 이전 버전과 같습니다.

검증
- 설치된 RDCMan 3.22 SDK와 앱의 실제 초기화 옵션을 맞춘 루프백 연결.
- 같은 조건에서 수정 전 대기/수정 후 NLA 인증 및 H.264 프레임 전송 비교.
- 구 엔진 NLA 연결, TLS 연결, 틀린 암호·계정 거절, 한글 포함 암호.
- 최종 배포 DLL에서 오디오/GPU 채널 및 정상→틀린 암호→정상 재접속 검사.
- 사용자 서피스 간 실제 LAN 연결은 업데이트 후 확인이 필요합니다.
- 기본 화면 공유 실험 버전이며 잠금/UAC 보안 화면, 로그인 전 접속은 지원하지 않습니다.

계속 실패하면 접속 시도 직후 로그를 저장해 주세요.
