## Windows의 두 모니터를 별도 창으로 표시 0.7.0-local (2026-11-03)

사용자는 같은 모니터의 복제 창 대신 Windows의 물리 모니터 1·2를 각각 볼 수 있도록 요청했습니다. Windows 서버에 선택적 전체 확장 모니터 캡처를 추가하고, Mac 클라이언트에 모니터 배치 수신·개별 화면 자르기·입력 좌표 변환·모니터 선택 메뉴를 추가했습니다. 서버의 한 연결을 공유하며 마지막 창을 닫을 때만 연결을 종료합니다.

- Windows: EnumDisplayMonitors로 장치 번호 순서의 배치를 확인하고 DXGI를 모니터별로 생성·합성합니다. 자동 모드 실패 시 GDI가 전체 가상 데스크톱을 캡처합니다. 마우스 절대 입력은 가상 데스크톱 좌표를 사용합니다. 기존 기본값은 주 모니터만 공유이며, 업데이트에 포함된 `WinHomeDesk-all-monitors.flag`로 전체 공유를 선택합니다. Windows GUI·RDCMan·오디오·IME 설정은 변경하지 않습니다.
- Mac: 표준 Monitor Layout PDU와 GFX ResetGraphics의 배치를 수신합니다. 음수 원점을 화면 버퍼 좌표로 변환하고, 각 창에서 해당 영역만 표시합니다. 모니터 선택과 `다른 모니터 새 창`, 앱의 `창` 메뉴를 추가했습니다.
- Mac arm64 빌드·패키징·deep/strict 서명 검사 통과. 전체 회귀 시험 통과: 입력/인증 10항목, 영상 8조합, 기존 오디오·여러 연결 창, 키 입력·종료·GPU/CPU 코덱 시험 포함.
- 모니터 geometry ASan/UBSan: 음수 좌표, 서로 다른 해상도, 세로 화면, 모니터별 화질 상한, 8192픽셀 전체 화면 상한, 잘못된 배치 거부 통과.
- 실제 AppKit 뷰: 가로·세로 자르기의 픽셀 색, 여백이 있는 창의 마우스 좌표·경계 제한, 잘못된 원격 배치 거부 통과.
- 합성 RDP 통합: 음수 X/음수 Y 배치 × AVC420/Bitmap = **4/4 통과**. 실제 인증·모니터 정보·두 창의 서로 다른 원본 영역·한 창 종료 후 다른 창 유지 확인. 가로 배치의 `(600,300)`/`(200,300)`, 세로 배치의 `(400,450)`/`(400,150)` 클릭이 서버 프로토콜 로그에 도착함을 검사했습니다. 실제 OS 입력은 없는 루프백 전용 시험입니다.
- Windows x64 교차 빌드 성공: 공식 LLVM-MinGW 20261020, MSYS2 OpenSSL 3.6.5/OpenH264 2.7.0 등 SHA256 확인. 엔진 패키지의 15개 파일과 모든 PE import 의존성을 검사했습니다. 설치 도구는 실행 전 DLL·모니터 열거 검사, SHA256 확인, 기존 엔진 백업·복사 검증·실패 시 복원을 수행하도록 구현했습니다.

원시 결과: `work/mac-monitor-{build,regression,test}.log`, `work/windows-monitor-{bootstrap,build,rebuild}.log`, `output/macos/monitor-results.json`, `output/windows-multimonitor/{engine-sha256,dependency-audit}.json`. Windows용 업데이트 폴더를 사용자가 지정한 OneDrive 설치 폴더 옆에 복사·해시 검사한 뒤 사용자가 Windows에서 설치 도구를 실행했습니다.

Windows 실기 적용: 사용자가 업데이트 완료 및 서버 재시작을 확인했습니다. OneDrive로 동기화된 설치 도구의 `monitor-preflight.txt`에서도 실제 새 Windows 엔진이 실행되어 `MONITOR_LIST count=2 width=3840 height=1200`을 출력한 것을 확인했습니다. 주 모니터는 `(0,0)`의 1920×1200, 보조 모니터는 `(1920,0)`의 1920×1200으로 열거됐습니다.

**실제 두 모니터 화면 및 입력 검증 통과:** 사용자가 최종 Mac 앱에 암호를 입력하고 인증서를 확인한 뒤 `WINDOWS_HOST:3390`에 연결했습니다. 전체 화면에서 탐색기가 열린 모니터 1과 바탕화면인 모니터 2가 서로 다르게 수신됐습니다. 모니터 1 선택 후 `다른 모니터 새 창`으로 모니터 2가 자동 선택된 별도 창이 열렸고 두 창 제목과 화면을 각각 확인했습니다. 모니터 2의 바탕화면에서 우클릭한 위치에 바탕화면 메뉴가, 모니터 1의 탐색기에서 우클릭한 위치에 탐색기 메뉴가 열리는 것을 관측했습니다. 각 창의 Escape 키로 메뉴가 닫혔습니다. 모니터 1 창을 닫아도 모니터 2가 연결된 채 유지됐으며, 암호 재입력 없이 모니터 1 창을 다시 열었습니다. 최종 상태는 두 창 모두 연결됨입니다. 실제 서버의 DXGI/GDI 강제 전환별 비교와 혼합 DPI/회전 배치 실기는 수행하지 않았으며 합성 배치 시험과 구분합니다.

최종 입력 보완: 뷰 포커스가 바뀔 때 누른 마우스 버튼만 마지막 원격 좌표에서 해제하도록 수정했습니다. 기존 코드의 무조건 `(0,0)` 버튼 해제가 Windows의 절대 이동으로 처리되어 커서가 다른 모니터 모서리로 이동할 수 있었습니다. 가로/세로 × AVC420/Bitmap 4조합에서 누름·포커스 이탈 해제가 모두 같은 모니터 좌표로 서버에 도착하고 `(0,0)` 이벤트가 없는 것을 확인했습니다. Backspace 9항목, 기존 미디어/여러 창 4항목도 재통과했습니다. 기록: `work/mac-monitor-final-build.log`, `work/mac-monitor-focus-test.log`. 최종 Mac 앱을 적용하고 기존 LAN 허용을 갱신한 뒤 실제 Windows NLA 응답 정상 확인.

## 같은 Windows PC의 새 창 연결 실패 수정 0.6.1-local (2026-11-03)

사용자가 같은 Windows PC의 새 창에서 연결 실패를 보고했습니다. GUI에서 `WINDOWS_HOST:3390`의 첫 창은 `Connected`, 후속 창들은 `0x0002000d`로 실패한 상태를 확인했습니다. Windows 런처 `work/SurfaceDesk.cs`는 `/max-connections:1`을 전달하며, 공통 shadow 서버는 제한에 도달하면 새 클라이언트를 인증 전에 거부합니다. 앞선 0.6.0 시험은 서로 다른 서버 두 개만 검증하여 이 조건을 놓쳤습니다.

같은 주소·포트·사용자·Domain의 새 창은 진행 중이거나 인증된 기존 RDP 연결을 공유하도록 수정했습니다. 창 크기·뷰·키 상태는 분리하고, 마지막 창을 닫을 때만 연결을 종료합니다. 다른 PC는 별도로 인증하며, 다른 계정·Domain에는 기존 연결을 재사용하지 않습니다. 새 연결의 빈 암호는 창을 만들기 전에 안내합니다. Windows 서버의 동시 접속 제한과 소스는 변경하지 않았습니다.

로컬 검증 통과:

- `/max-connections:1` 합성 서버에서 기존 방식의 두 번째 실제 RDP 접속이 동일한 `0x0002000d`로 실패함을 재현.
- 연결 중·연결 후 같은 PC의 새 창에서 클라이언트 하나 재사용, 화면 수신, 원본 창 종료 후 남은 창의 프레임 증가 확인.
- 다른 서버 동시 인증·화면 수신, 다른 계정/Domain/포트의 빈 암호 거부, 창별 종료, 마지막 창 종료 후 새 클라이언트로 재접속 확인.
- 공유 창이 포함된 앱 종료 대기, 입력 큐·Backspace 회귀, 기존 합성 rdpsnd 오디오 및 두 시험 서버 정상 종료 통과.
- arm64 앱 빌드·0.6.1 패키징·deep/strict 서명 검사 통과. `work/mac-multiwindow-fix-{build,test}.log`, `output/macos/media-results.json`에 결과 기록.

수정 앱의 기존 로컬 네트워크 허용을 다시 적용한 뒤 실제 Windows 서버의 TCP/NLA 응답을 확인했습니다. 사용자가 암호를 직접 입력하고 인증서를 이번 연결에 허용한 후, **0.6.1 앱에서 실제 Windows `WINDOWS_HOST:3390` 로그인·두 번째 창 화면 수신을 확인했습니다.** 두 번째 창은 암호나 인증서를 다시 묻지 않았고 메인 로그에 `Shared connection`을 기록했습니다. 두 번째 창에서 Windows 시작 메뉴를 클릭해 입력·화면 갱신을 확인하고, 그 창을 닫은 뒤 암호 재입력 없이 새 창을 다시 열어 같은 시작 메뉴 상태가 유지되는 것을 확인했습니다. 새 창의 Escape 입력으로 메뉴가 닫히는 갱신도 관측했습니다. 원래 창은 최소화된 상태로 유지했고, 마지막 확인용 새 창은 연결된 채 남겼습니다. 실제 여러 Windows PC 동시 접속은 여전히 미검증이며 서로 다른 합성 서버 두 개의 시험과 구분합니다.

## 오디오·지연·여러 연결 창 0.6.0-local (2026-11-03)

사용자는 소리가 필요한 방향을 **Windows RDCMan → Mac 서버**, 멀티윈도우를 **여러 원격 연결 창**으로 지정했습니다. Mac 시스템 재생음의 RDP 전송과 Mac 클라이언트의 독립 연결 창을 구현했습니다. 기존 Windows의 WASAPI·44.1 kHz 오디오 캡처·Media Foundation·GUI 소스는 수정하지 않았습니다.

- 시스템 오디오: ScreenCaptureKit 전용 스트림, 48 kHz/스테레오/PCM16, 10ms 패킷. 영상 압축과 분리. Windows 버전의 인증·활성화·협상 검사, 메시지 큐 8개 상한, 80ms 초과 데이터 폐기, 기존 공통 rdpsnd/Wave2/확인 통계 사용. 호환 스크린샷 영상에서도 시스템 소리 유지. 마이크 제외·녹음 파일 저장 없음.
- 커서: 영상 합성을 끄고 RDP 포인터 모양 전송, 수신 PC에서 즉시 움직임 표시. 현재 시스템 커서 모양 조회와 크기/핫스폿 변환, 변경 시 갱신·재연결을 위한 주기적 재전송. 이 API는 macOS에서 제공되지만 폐기 예정 표시가 있어 향후 OS 변경 시 재검증 필요.
- 영상/입력 대기: 자동 캡처는 프레임 도착 이벤트로 처리하고 최신 1개 유지. Mac 클라이언트 입력은 큐 추가 시 작업자를 깨우며, 연속 이동만 최신 위치로 합치고 키·클릭 순서를 보존. 새 이미지만 60Hz 공통 실행 루프에서 표시.
- 여러 연결 창: 각각 별도 클라이언트·인증·이미지·키 상태·종료 상태. 창별 호스트/포트 제목, 선택 연결 종료, 한 창 종료 시 나머지 유지, 앱 종료 시 모든 작업자 정리. Mac 서버의 제어자는 기존대로 한 명이며 다중 모니터 지원으로 확장한 것은 아님.

## 확인한 결함과 수정

- Windows 전용 probe / Media Foundation 소스가 Mac 빌드에 포함됨 → WIN32 조건 분리
- 공용 shadow helper의 Windows 헤더 의존성 → 비Windows에서 WinPR 헤더 사용
- NLA 사용자 이름의 Windows `wchar_t` 의존성 → 비Windows UTF-16 비교 경로
- 기존 Mac shadow의 오래된 CGDisplayStream, 비어 있는 Unicode 처리 → ScreenCaptureKit 및 Quartz 입력으로 대체
- Apple Right Control이 Right Windows로 매핑됨 → Apple 키 테이블 수정
- 실제 입력 시험의 종료 시 worker와 process-wide 정리가 경합 → 연결 종료 완료 후 프로세스 종료
- Mac 클라이언트의 Backspace(`0x7F`)를 일반 문자로 분류하고 AppKit 삭제 명령을 버림 → 물리 키 전송 및 삭제 selector 처리, 조합 중 Backspace는 로컬 IME가 소비하도록 분리
- 서버 시작 뒤 NSTask 환경 변경으로 예외 발생 → 실행 전에 암호 칸을 비우고 task 종료 시 참조 해제
- GUI가 `NSTerminateLater`를 반환한 후 기본 run loop의 타이머가 정지 → 종료 대기를 background queue로 옮기고 main queue에서 AppKit에 완료 통지
- RDCMan 2.93 한영 전환·한글 입력 실패 → Mac 서버의 전용 한영 키 누락을 보완하고 한국어 레이아웃의 오른쪽 Alt를 처리. macOS가 선택 불가능한 상위 입력기를 반환하는 경우 실제 활성화된 한국어 입력 모드를 선택하도록 추가 수정. 사용자 실기 재시험에서 양방향 전환·한글 입력 정상 확인

해당 LAN 세션의 연속 관측 구간에서 캡처→처리 시작 평균은 약 3.50~9.90ms, 영상 전송은 약 18.9~19.7 FPS였고 전송 오류는 없었습니다. 오디오의 서버 측 평균 age는 약 48~52ms, Windows 클라이언트가 보고한 hold 값은 약 116~121ms였습니다. Windows의 재생 버퍼 대기는 여전히 존재하며, 이를 10ms 패킷만큼의 종단간 음성 지연으로 주장하지 않습니다.

0.6.0 최종 실기 결과(2026-11-03): 사용자가 Windows에서 **소리·커서·화면 모두 정상**이라고 확인했습니다. 서버는 시스템 소리 공유·분리 커서·GPU AVC420·1920×1080/20 FPS 목표 설정으로 실행 중입니다. 로컬 구현·빌드·회귀 시험과 RDCMan 3.22 청취/조작 시험을 완료했습니다. 기존 Windows 기능 소스는 유지했고 GitHub push·릴리스 게시·commit·tag는 수행하지 않았습니다.
